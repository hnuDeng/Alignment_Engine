## 一、反事实场景分析

### 1.1 场景1：LLM分解完全失败

**假设：** LLM无法准确分解任何任务。

**后果：**
1. 系统完全无法工作
2. 需要完全依赖规则分解
3. 灵活性大幅降低

**应对策略：**
1. **回退到规则分解**：使用预定义规则
2. **混合方法**：LLM + 规则结合
3. **简化任务**：只处理简单任务

**关键问题：**
- LLM分解失败的概率有多大？
- 规则分解是否足够？
- 如何设计混合方法？

### 1.2 场景2：运动原语库覆盖不足

**假设：** 预定义的运动原语库无法覆盖任何实际任务。

**后果：**
1. 系统无法执行任何任务
2. 需要大量新原语
3. 系统不可用

**应对策略：**
1. **学习新原语**：从示范中学习
2. **组合原语**：组合现有原语
3. **直接生成**：跳过原语，直接生成轨迹

**关键问题：**
- 原语库覆盖不足的概率有多大？
- 学习新原语是否可行？
- 直接生成是否可行？

### 1.3 场景3：双循环不收敛

**假设：** 双循环验证无法收敛，总是失败。

**后果：**
1. 系统无法完成任何任务
2. 浪费计算资源
3. 用户体验差

**应对策略：**
1. **设置最大迭代次数**：避免无限循环
2. **回退到单循环**：放弃双循环
3. **简化任务**：只处理简单任务

**关键问题：**
- 双循环不收敛的概率有多大？
- 最大迭代次数如何设置？
- 回退策略是否有效？

### 1.4 场景4：物理验证器不准确

**假设：** 物理验证器总是误判。

**后果：**
1. 可行轨迹被拒绝
2. 不可行轨迹被接受
3. 系统不可靠

**应对策略：**
1. **多重验证**：使用多个验证器
2. **保守验证**：使用更严格的标准
3. **真实验证**：在真实环境中验证

**关键问题：**
- 验证器不准确的概率有多大？
- 多重验证是否有效？
- 保守验证是否过于保守？

### 1.5 场景5：LLM产生幻觉

**假设：** LLM产生不存在的物体或动作。

**后果：**
1. 系统尝试操作不存在的物体
2. 导致碰撞或失败
3. 安全性无法保证

**应对策略：**
1. **验证机制**：检查LLM输出的物体是否存在
2. **置信度阈值**：只接受高置信度的输出
3. **多LLM投票**：使用多个LLM，取共识

**关键问题：**
- LLM产生幻觉的概率有多大？
- 验证机制是否有效？
- 多LLM投票是否有效？

## 七、检查点设计

### 7.1 检查点1：LLM分解验证（2周）

**目标：** 验证LLM分解能力

**检查内容：**
- LLM分解准确率
- 失败案例分析
- 回退机制测试

**成功标准：** 准确率 > 70%

**失败处理：** 如果准确率 < 50%，回退到规则分解

**目标：** 验证原语库覆盖度

**检查内容：**
- 原语库覆盖度
- 新原语需求
- 组合机制测试

**成功标准：** 覆盖度 > 70%

**失败处理：** 如果覆盖度 < 50%，学习新原语

### 7.3 检查点3：双循环收敛验证（6周）

**目标：** 验证双循环收敛性

**检查内容：**
- 迭代次数
- 收敛率
- 不收敛案例分析

**成功标准：** 平均迭代次数 < 5

**失败处理：** 如果平均迭代次数 > 10，简化为单循环

**目标：** 验证系统整体性能

**检查内容：**
- 任务成功率
- 规划时间
- 与Baseline对比

**成功标准：** 成功率 > 70%

**失败处理：** 如果成功率 < 50%，重新设计
