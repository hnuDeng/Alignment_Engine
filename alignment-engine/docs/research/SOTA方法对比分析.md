# 时间：2026-09-18

## 一、当前SOTA方法概述

### 1.1 路线1代表方法

**PlaNet (2019)**
- 核心：潜在空间世界模型 + CEM规划
- 优势：端到端学习，无需真实模型
- 劣势：CEM容易陷入局部最优

**DreamerV3 (2023)**
- 核心：潜在空间世界模型 + Actor-Critic
- 优势：单一配置在150+任务上超越专用方法
- 劣势：依赖奖励函数设计

**TD-MPC2 (2023)**
- 核心：隐式世界模型 + 局部轨迹优化
- 优势：计算效率高，泛化能力强
- 劣势：局部优化可能陷入局部最优

### 1.2 路线4代表方法

**CAPE (2026)**
- 核心：对比动作条件并行编码
- 优势：并行生成多个轨迹
- 劣势：计算开销大

**LeFlow (2026)**
- 核心：生成式潜在流规划
- 优势：流匹配比扩散更稳定
- 劣势：需要大量训练数据

**Latent Diffusion Planning (2024)**
- 核心：潜在空间扩散规划
- 优势：可以生成多模态轨迹
- 劣势：推理速度慢

### 1.3 LLM辅助规划方法

**SayCan (2022)**
- 核心：LLM评分 + 技能库
- 优势：利用LLM理解任务
- 劣势：依赖技能库覆盖

**Code as Policies (2023)**
- 核心：LLM生成Python代码
- 优势：灵活，可组合
- 劣势：安全风险，依赖代码质量

**Inner Monologue (2023)**
- 核心：LLM推理 + 环境反馈
- 优势：闭环规划
- 劣势：依赖反馈质量

## 二、我们的方案 vs SOTA方法

### 2.1 核心差异

| 维度 | 我们的方案 | SayCan | Code as Policies | DreamerV3 |
|------|------------|--------|------------------|-----------|
| 任务分解 | LLM分层分解 | LLM评分 | LLM生成代码 | 无 |
| 动作表示 | 运动原语 | 技能库 | Python代码 | 连续动作 |
| 参数优化 | 梯度优化 | 无 | 无 | Actor-Critic |
| 验证机制 | 物理验证器 | 无 | 无 | 无 |
| 反馈机制 | 双循环反馈 | 单次规划 | 单次规划 | 奖励信号 |
| 泛化能力 | 原语组合 | 技能库覆盖 | 代码泛化 | 世界模型泛化 |

### 2.2 创新点对比

**创新点1：分层任务分解**
- 我们：LLM分层分解任务为子任务序列
- SayCan：LLM评分选择技能
- Code as Policies：LLM生成代码
- 差异：我们有明确的层次结构和依赖关系

**创新点2：运动原语库**
- 我们：预定义 + 学习的运动原语库
- SayCan：预训练的技能库
- Code as Policies：Python函数库
- 差异：我们的原语有明确的参数化和物理约束

**创新点3：双循环验证**
- 我们：物理验证器验证 + 反馈重规划
- SayCan：单次规划
- Code as Policies：代码执行
- 差异：我们有闭环反馈机制

**创新点4：参数优化**
- 我们：梯度优化原语参数
- SayCan：无参数优化
- Code as Policies：无参数优化
- 差异：我们可以优化轨迹质量

### 2.3 理论优势

**优势1：更好的任务分解**
- 分层分解降低了每层的复杂度
- 依赖关系确保了执行顺序
- 前置/后置条件确保了正确性

**优势2：更好的泛化能力**
- 运动原语可以组合
- 原语可以学习
- 新任务可以通过组合原语完成

**优势3：更好的鲁棒性**
- 物理验证器确保轨迹可行
- 双循环反馈可以纠正错误
- 重规划机制可以处理失败

**优势4：更好的可解释性**
- 分层结构清晰
- 原语语义明确
- 验证结果可解释

## 三、潜在劣势分析

### 3.1 劣势1：实现复杂度高

**问题：** 我们的方案需要实现多个组件。

**对比：**
- SayCan：只需要LLM + 技能库
- Code as Policies：只需要LLM
- 我们：需要LLM + 任务分解器 + 原语库 + 原语选择器 + 参数优化器 + 轨迹生成器 + 物理验证器

**缓解措施：**
- 模块化设计，每个组件独立
- MVP方法，先实现核心功能
- 迭代开发，逐步完善

### 3.2 劣势2：依赖LLM准确性

**问题：** 我们的方案依赖LLM准确分解任务。

**对比：**
- DreamerV3：不依赖LLM，端到端学习
- TD-MPC2：不依赖LLM，隐式世界模型
- 我们：依赖LLM分解任务

**缓解措施：**
- 多LLM投票
- 验证机制
- 回退机制

### 3.3 劣势3：原语库覆盖度

**问题：** 我们的方案依赖原语库覆盖所有任务。

**对比：**
- Code as Policies：可以生成任意代码
- DreamerV3：可以学习任意动作
- 我们：只能使用预定义或学习的原语

**缓解措施：**
- 学习机制
- 组合机制
- 扩展机制

### 3.4 劣势4：计算开销

**问题：** 我们的方案需要多次LLM调用和优化。

**对比：**
- SayCan：单次LLM调用
- DreamerV3：单次前向传播
- 我们：多次LLM调用 + 多次优化

**缓解措施：**
- 缓存机制
- 并行处理
- 近似优化

## 四、实验对比设计

### 4.1 实验环境

**仿真环境：** RLBench（机器人操作benchmark）

**任务选择：**
1. 简单任务：pick_and_place（10个变体）
2. 中等任务：stack_blocks（10个变体）
3. 复杂任务：set_table（10个变体）

### 4.2 Baseline方法

1. **SayCan**：LLM评分 + 技能库
2. **Code as Policies**：LLM生成代码
3. **DreamerV3**：潜在空间世界模型
4. **TD-MPC2**：隐式世界模型

### 4.3 评估指标

| 指标 | 计算方法 | 说明 |
|------|----------|------|
| 任务成功率 | 成功任务数 / 总任务数 | 主要指标 |
| 规划时间 | 从指令到轨迹的时间 | 效率指标 |
| 迭代次数 | 双循环平均迭代次数 | 收敛性指标 |
| 物理可行性 | 可行轨迹数 / 总轨迹数 | 安全性指标 |
| 泛化成功率 | 新任务成功数 / 新任务数 | 泛化能力指标 |

### 4.4 预期结果

| 方法 | 简单任务 | 中等任务 | 复杂任务 | 平均 |
|------|----------|----------|----------|------|
| SayCan | 90% | 60% | 30% | 60% |
| Code as Policies | 85% | 55% | 25% | 55% |
| DreamerV3 | 80% | 50% | 20% | 50% |
| TD-MPC2 | 75% | 45% | 15% | 45% |
| 我们的方案（预期） | 95% | 80% | 60% | 78% |

### 4.5 成功标准

如果我们的方案在复杂任务上成功率超过50%，且平均成功率超过70%，则认为实验成功。

## 六、总结

### 6.1 核心优势

1. **更好的任务分解**：分层分解降低复杂度
2. **更好的泛化能力**：原语组合提高泛化
3. **更好的鲁棒性**：双循环验证提高鲁棒性
4. **更好的可解释性**：分层结构清晰可解释

### 6.2 潜在劣势

1. **实现复杂度高**：需要实现多个组件
2. **依赖LLM准确性**：LLM分解可能失败
3. **原语库覆盖度**：可能无法覆盖所有任务
4. **计算开销大**：需要多次LLM调用和优化

### 6.3 缓解措施

1. **模块化设计**：降低实现复杂度
2. **多LLM投票**：提高LLM准确性
3. **学习机制**：扩展原语库覆盖度
4. **缓存机制**：降低计算开销

### 6.4 最终评价

我们的方案在理论上优于现有SOTA方法，但需要实验验证。核心创新点是分层LLM规划 + 运动原语库 + 双循环验证，这三点都是现有方法所缺乏的。如果实验验证成功，将是一个重要的贡献。
